# 原生 ISO 播放排查与按需读盘实现

日期：2026-10-06。

伪装 ISO 实际仍是 MKV、MP4 等视频容器，识别文件头后可以走普通视频播放。原生 ISO 需要解析光盘文件系统、选择正片、处理播放列表和片段导航，再封装或转码为浏览器视频。本次已把成熟的 libbluray 读盘能力接到项目的随机读取器上，让受支持的远程蓝光无需先缓存整张 ISO。

## 已确认的问题与修复

| 环节 | 原有问题 | 当前行为 |
| --- | --- | --- |
| 简化蓝光播放列表 | 任意一个 MPLS 解析失败就终止整盘按需读取，短菜单也能触发完整缓存 | 分别评估时长和可读性；无关短列表不阻断正片，复杂最长主片不会被短预告替代 |
| 正式蓝光导航 | 仅按 MPLS 拼接 M2TS，不能完整处理 CLPI 导航、片段预读和时间戳 | 有索引或 CLPI 的光盘优先使用 libbluray；主片、默认角度和片段导航交给读盘库 |
| 复杂蓝光 | 原来的 FFmpeg `bluray:` 路径要求可访问的本地镜像，远程盘因此先下载完整 ISO | 新增独立读盘进程，通过 `bd_open_stream` 回调读取私有 HTTP Range 镜像视图，提供可跳转的正片流 |
| 源文件读取 | 目录和正片都按 256 KiB 读取，串行请求放大网络延迟；本地 UDF 强制走提取路径 | 目录按 256 KiB、正片按 4 MiB 读取；每任务保留最多 8 MiB 源数据块，本地文件也按需读取并复用缓存 |
| 构建与任务显示 | 只有远程分段与整盘缓存说明 | Docker 和更新包构建包含组件；播放与缓存页面识别远程/本地原生蓝光按需模式 |

正式蓝光样本暴露了另一个实质性问题：12 秒、两段 M2TS 的自制光盘，使用简化拼接路径时输出时长被误算为 624.063 秒。增加原生导航优先路径后，输出恢复到正确时长，从第 5 秒起播也正常。这也是正式蓝光即使播放列表呈线性结构，仍优先使用 libbluray 的原因。

## 磁盘依赖减少到哪里

受支持的远程蓝光现在按下面的链路播放：

`网盘 Range → 有上限的源块缓存 → 私有镜像视图 → libbluray 读盘进程 → 私有正片视图 → FFmpeg → 网页播放输出`

组件只收到随机路径的回环地址，外网源地址和凭据留在 Go 服务内；两个临时监听均只绑定 `127.0.0.1`。组件通过标准输入输出接收定位请求、返回正片数据，不写源镜像或中间正片文件。任务取消时同时停止读盘进程、取消上游读取并关闭监听。

源数据块缓存最多 8 MiB，并不代表整个任务只占 8 MiB 内存；读盘库、HTTP 和 FFmpeg 另有工作缓冲。目录阶段限制请求量和耗时，复杂目录失败后会给原生读盘一次独立的有界探测机会。正片阶段切换到任务上下文，避免被已结束的目录探测计时误杀。

网页播放输出依然保留磁盘缓存，方便浏览器 Range 播放和当前任务管理。网盘不支持可靠 Range、组件缺失、盘损坏或结构无法读取时，现有完整缓存回退仍保留；这条回退仍要求足够磁盘。此次没有宣称所有路径都能零磁盘播放。

## 验证证据

16 种 FFmpeg 播放集成场景全部通过：

- 原有 11 种：伪装 MKV、远程 DVD、镜像内普通视频、不支持 Range 的完整缓存回退、远程简化蓝光、超过缓存预算的大镜像、蓝光从第 5 秒起播、带短菜单的远程/本地蓝光、本地蓝光跳转、本地 DVD。
- 新增 5 种：多角度原生蓝光的远程大镜像、远程跳转、本地起播、本地跳转，以及 tsMuxeR 直接生成的 UDF 2.50 蓝光。

大镜像测试将小样本映射为 **64 GiB 虚拟镜像**，播放缓存配置为 **1 GiB**，上游拒绝任何不带 Range 的整盘 GET。按需播放仍成功，任务目录没有生成 `source.iso`。该测试验证大小限制不会强迫下载全盘，不能代表实际 64 GiB 电影的吞吐量或完整观看效果。

播放输出检查覆盖 H.264/AAC、正确正片时长、播放输出 Range 和从第 5 秒起播。新增读盘检查进一步覆盖：

- 将任意字节位置的跳转结果与顺序读取结果逐字节比较，包括跨片段和非 192 字节对齐的位置。
- 多角度样本使用不同画面和音调的备用角度，解码默认角度首帧并与原始视频哈希对比。
- 暂停时正片读取保持等待，恢复后继续返回相同的正片数据。
- 上游读取被阻塞时取消任务，确认读盘进程、客户端读取、上游请求均及时结束，监听不再可访问。

回归测试另覆盖主片选择、错误 Range 拒绝、源块缓存上限、目录上下文切换、暂停/恢复、权限、删除、过期和快速重开任务。连续读取对齐的 12 MiB 数据，正片源请求数从 48 次降到 3 次；这说明请求开销下降，不等于网盘端到端速度提升 16 倍。

Linux Go 编译与 `go vet`、读盘组件按 Docker 所用加固参数编译、修改的 JavaScript 语法检查通过；现有更新脚本的 7 项测试通过。另构造更新归档，确认现有更新器接受组件源码的发布路径并能完整提取。数据库集成检查使用独立临时数据库与角色，测试结束后删除。Docker 引擎未运行，完整镜像构建和线上部署尚未验证。

## 复现与边界

`scripts/make-bluray-test-fixtures.py` 使用 FFmpeg、tsMuxeR、genisoimage 生成可重复的未加密样本。它先制作 12 秒、双片段、含索引与 CLPI 的蓝光，再生成 UDF 2.50 镜像与独立备用角度。测试用 `ISO_NATIVE_FIXTURE_ROOT` 指向输出目录，原有样本仍通过 `ISO_FIXTURE_ROOT` 指定。

这次验证使用自制样本，尚未拿到用户当前播放失败的实际镜像，也不能覆盖所有商业盘、播放列表混淆或特殊子路径。主片仍按最长时长选择，不提供完整光盘菜单。组件拒绝检测到的 AACS/BD+ 加密盘，不包含解密能力。

实现使用 [libbluray 官方流读取回调 API](https://videolan.videolan.me/libbluray/bluray_8h.html)。原有本地回退路径可对照 [FFmpeg 的 bluray 实现](https://ffmpeg.org/doxygen/trunk/bluray_8c_source.html)。测试制作工具来自 [tsMuxer 官方仓库](https://github.com/justdan96/tsMuxer)；Go UDF 依赖及能力说明见 [golift/udf](https://github.com/golift/udf)。组件构建与进程协议见 [disc-reader/README.md](../disc-reader/README.md)。
